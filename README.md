# Monitoring Prototype

> Программный комплекс для централизованного мониторинга Linux-серверов с модулем прогнозирования состояния вычислительной инфраструктуры на основе модели ARIMA.

## О проекте

**Monitoring Prototype** — распределённая система мониторинга Linux-серверов, предназначенная для автоматизированного сбора, хранения, анализа и визуализации системных метрик.

Комплекс позволяет отслеживать состояние вычислительной инфраструктуры в режиме реального времени, анализировать историю изменения показателей, прогнозировать возможные отклонения и своевременно уведомлять администратора о возникновении критических ситуаций.

В состав системы входят:

- агент мониторинга на C++;
- серверная часть на фреймворке Drogon;
- база данных PostgreSQL;
- кэш Redis;
- аналитический модуль прогнозирования на Python;
- веб-интерфейс администратора;
- обратный прокси Nginx.

---

# Основные возможности

- автоматический сбор системных метрик Linux;
- безопасная передача данных по HTTPS;
- аутентификация агентов по API-ключам;
- хранение исторических данных;
- визуализация текущих и архивных метрик;
- прогнозирование состояния системы на основе модели ARIMA;
- автоматическое формирование оповещений;
- отправка уведомлений по электронной почте;
- кэширование данных с использованием Redis;
- развёртывание комплекса с помощью Docker Compose;
- автоматическая установка агента мониторинга.

# Компоненты системы

## Агент мониторинга

Агент устанавливается на каждый контролируемый Linux-сервер и работает как системная служба (`systemd`).

Функции агента:

- сбор системных метрик;
- формирование JSON-пакетов;
- передача данных по HTTPS;
- буферизация данных при отсутствии соединения;
- автоматическая повторная отправка накопленных метрик после восстановления связи.

Сбор метрик осуществляется каждые **10 секунд**.

---

## Серверная часть

Сервер реализован на языке **C++** с использованием фреймворка **Drogon**.

Основные функции:

- приём метрик;
- проверка API-ключей;
- сохранение данных;
- REST API;
- обработка запросов веб-интерфейса;
- управление пользовательскими сессиями;
- взаимодействие с Redis;
- запуск прогнозирования;
- формирование оповещений.

---

## PostgreSQL

Используется для долговременного хранения данных.

В базе данных сохраняются:

- зарегистрированные агенты;
- системные метрики;
- результаты прогнозирования;
- события оповещения.

---

## Redis

Redis используется для:

- хранения пользовательских сессий;
- кэширования данных дашборда;
- временного хранения служебной информации.

Использование Redis позволяет существенно уменьшить нагрузку на PostgreSQL.

---

## Модуль прогнозирования

Аналитический сервис реализован на языке Python.

Используется библиотека **statsmodels** и модель **ARIMA(1,1,1)**.

Модуль:

- получает исторические данные;
- строит модель временного ряда;
- формирует прогноз;
- сохраняет результаты в PostgreSQL;
- используется системой оповещений.

---

## Веб-интерфейс

Пользовательский интерфейс разработан с использованием:

- HTML;
- CSS;
- JavaScript;
- Chart.js.

Возможности интерфейса:

- просмотр текущего состояния серверов;
- отображение графиков;
- просмотр истории изменения метрик;
- просмотр результатов прогнозирования;
- отображение списка оповещений.

# Собираемые метрики

Агент мониторинга передаёт следующие показатели:

| Метрика | Описание |
|----------|----------|
| CPU | загрузка процессора |

# Принцип работы

1. Агент собирает системные метрики Linux.
2. Метрики сериализуются в JSON.
3. Данные отправляются на сервер по HTTPS.
4. Сервер проверяет API-ключ.
5. Метрики сохраняются в PostgreSQL.
6. Redis обновляет кэш дашборда.
7. Аналитический модуль строит прогноз.
8. При необходимости формируются оповещения.
9. Администратор получает уведомление по электронной почте.

# Быстрый запуск

Развёртывание программного комплекса выполняется в два этапа:

# Подготовка сервера

Перейдите в каталог проекта.

```bash
cd monitoring-prototype
```

Запустите сценарий первоначальной настройки.

```bash
sudo ./server/setup.sh
```

Скрипт автоматически выполнит следующие действия:

- проверит наличие Docker и Docker Compose;
- сгенерирует самоподписанный SSL-сертификат (если он отсутствует);
- создаст конфигурационный файл SMTP;
- соберёт все Docker-образы.

Во время выполнения будет создан файл

```
config/server.conf
```

со следующими параметрами:

```ini
SMTP_HOST=smtp.yandex.com
SMTP_PORT=465
SMTP_FROM=your-email@yandex.com
SMTP_PASSWORD=your-app-password
SMTP_TO=admin@example.com
```

Перед запуском системы рекомендуется указать параметры SMTP-сервера, которые будут использоваться для отправки уведомлений администраторам.

---

# Запуск системы

После завершения настройки выполните:

```bash
docker compose up -d
```

Проверить состояние контейнеров можно командой:

```bash
docker compose ps
```

Просмотреть журналы работы всех сервисов:

```bash
docker compose logs -f
```

Для остановки комплекса:

```bash
docker compose down
```

# Установка агента мониторинга

Агент устанавливается отдельно на каждый Linux-сервер, который необходимо подключить к системе мониторинга.

Перейдите в каталог агента.

```bash
cd agent
```

Запустите установочный сценарий.

```bash
sudo ./install-agent.sh
```

При необходимости параметры можно передать непосредственно в командной строке.

Например:

```bash
sudo ./install-agent.sh \
YOUR_API_KEY \
https://monitor.example.com:8443/api/metrics
```

В этом случае файл конфигурации будет создан автоматически.

---

# Конфигурация агента

После установки создаётся файл

```
/etc/monitoring-agent/config
```

Пример содержимого:

```ini
API_KEY=YOUR_API_KEY
SERVER_URL=https://monitor.example.com:8443/api/metrics
```

Описание параметров:

| Параметр | Описание |
|----------|----------|
| `API_KEY` | API-ключ агента, используемый для аутентификации |
| `SERVER_URL` | URL конечной точки сервера мониторинга для отправки метрик |

---

# Управление агентом

Агент устанавливается как служба `systemd`.

Запуск:

```bash
sudo systemctl start monitoring-agent
```

Остановка:

```bash
sudo systemctl stop monitoring-agent
```

Перезапуск:

```bash
sudo systemctl restart monitoring-agent
```

Проверка состояния:

```bash
sudo systemctl status monitoring-agent
```

Просмотр журнала:

```bash
sudo journalctl -u monitoring-agent -f
```

---

# Удаление агента

Для полного удаления агента используйте сценарий:

```bash
sudo ./uninstall-agent.sh
```

Во время удаления будут автоматически:

- остановлена и отключена служба `monitoring-agent`;
- удалён исполняемый файл;
- удалён файл конфигурации;
- удалены журналы;
- удалён локальный буфер метрик;
- удалён systemd-сервис.

Если в буфере присутствуют неотправленные данные, сценарий предложит сохранить их перед удалением.

# REST API

Серверная часть предоставляет REST API для взаимодействия с агентами мониторинга и веб-интерфейсом.

API можно условно разделить на две группы:

- API агентов мониторинга;
- API панели администратора.

Большинство методов панели администратора требуют прохождения аутентификации. После успешного входа сервер создаёт пользовательскую сессию и сохраняет её в Redis. Все последующие запросы выполняются с использованием cookie `session_id`.

---

# Аутентификация

## Вход в систему

```
POST /api/login
```

Авторизация пользователя.

### Тело запроса

```json
{
    "username": "admin",
    "password": "admin"
}
```

### Успешный ответ

```http
HTTP/1.1 200 OK
```

```json
{
    "status": "ok"
}
```

При успешной авторизации сервер устанавливает cookie:

```
session_id=...
```

который автоматически используется браузером при дальнейшей работе.

---

# Регистрация агента

```
POST /api/agents
```

Создаёт нового агента мониторинга и автоматически генерирует API-ключ.

> Требуется авторизация администратора.

### Запрос

```json
{
    "name": "web-server-01"
}
```

### Ответ

```json
{
    "id": 1,
    "name": "web-server-01",
    "api_key": "xxxxxxxxxxxxxxxx"
}
```

Полученный API-ключ необходимо указать в конфигурации агента.

---

# Получение списка агентов

```
GET /api/agents
```

Возвращает список зарегистрированных агентов.

Для каждого агента отображаются:

- идентификатор;
- имя;
- время последнего подключения;
- текущий статус (Online / Offline).

Используется веб-интерфейсом для заполнения списка серверов.

---

# Отправка метрик

```
POST /api/metrics
```

Основной метод взаимодействия агента с сервером.

Агент отправляет набор системных метрик в формате JSON.

### Заголовки

```
X-API-Key: <API_KEY>
Content-Type: application/json
```

### Ответ

```http
200 OK
```

При неверном API-ключе сервер возвращает

```http
401 Unauthorized
```

---

# Получение последних метрик

```
GET /api/metrics/latest?agent_id=<id>
```

Возвращает последнее полученное состояние выбранного сервера.

Используется для отображения карточек текущего состояния (KPI) на панели мониторинга.

---

# Получение истории

```
GET /api/metrics/history
```

### Параметры

| Параметр | Описание |
|----------|----------|
| agent_id | идентификатор агента |
| period | период в часах |

Пример:

```
GET /api/metrics/history?agent_id=1&period=72
```

Ответ содержит временной ряд выбранного сервера за указанный период.

---

# Получение прогноза

## Построение прогноза

```
GET /api/forecast/{agent_id}/{metric}
```

Запускает построение прогноза выбранной метрики.

---

## Получение сохранённого прогноза

```
GET /api/forecast/stored/{agent_id}/{metric}
```

Возвращает ранее рассчитанный прогноз.

Используется веб-интерфейсом для отображения прогнозной части графика.

---

# Работа с оповещениями

## Получение списка

```
GET /api/alerts
```

Возвращает список зарегистрированных оповещений.

Для каждого события отображаются:

- сервер;
- тип события;
- время возникновения;
- статус обработки.

---

## Подтверждение оповещения

```
POST /api/alerts/{id}/resolve
```

Помечает выбранное оповещение как обработанное.

После подтверждения событие остаётся в истории, но перестаёт отображаться как активное.

---

# Формат передаваемых метрик

Агент мониторинга передаёт данные на сервер посредством HTTP-запроса

```
POST /api/metrics
```

с заголовками

```
Content-Type: application/json
X-API-Key: <API_KEY>
```

---

# Формат JSON

Каждый запрос содержит один набор метрик.

Пример:

```json
{
    "cpu": 18.45,
    "memory": 41.72,
    "ram": 41.72,
    "swap": 0.00,
    "load_avg": 0.37,
    "processes_running": 153,
    "network_rx": 18452,
    "network_tx": 9321,
    "timestamp": 1718235812456
}
```

---

# Описание полей

| Поле | Тип | Описание |
|------|-----|----------|
| `cpu` | `double` | загрузка процессора, % |
| `memory` | `double` | использование оперативной памяти, % |
| `ram` | `double` | использование оперативной памяти, % (дублирует поле `memory`) |
| `swap` | `double` | использование раздела подкачки, % |
| `load_avg` | `double` | средняя нагрузка системы (Load Average за последнюю минуту) |
| `processes_running` | `integer` | количество процессов, находящихся в состоянии выполнения |
| `network_rx` | `integer` | скорость входящего сетевого трафика, байт/с |
| `network_tx` | `integer` | скорость исходящего сетевого трафика, байт/с |
| `timestamp` | `integer` | время формирования пакета в миллисекундах Unix Epoch |

---

# Требования к запросу

Сервер ожидает корректный JSON-документ.

Также должны соблюдаться следующие условия:

- используется метод `POST`;
- указан заголовок `Content-Type: application/json`;
- указан заголовок `X-API-Key`;
- JSON содержит полный набор обязательных полей.

---

# Пример передачи метрик

```bash
curl -k \
-X POST \
-H "Content-Type: application/json" \
-H "X-API-Key: YOUR_API_KEY" \
-d '{
    "cpu": 16.2,
    "memory": 37.9,
```

# Разработка собственного агента

Протокол обмена является открытым.

Любое приложение, способное выполнять HTTPS-запросы, может использоваться в качестве агента мониторинга при соблюдении следующих требований:

- отправка выполняется методом `POST`;
- используется конечная точка `/api/metrics`;
- передаётся корректный API-ключ;
- тело запроса соответствует указанному формату JSON.

Благодаря этому агент мониторинга может быть реализован на любом языке программирования, поддерживающем работу с HTTP и JSON.
